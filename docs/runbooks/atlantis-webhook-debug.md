The decision tree, symptom-first:

1. **No comment on the PR at all.** Check `curl -sf $ATLANTIS_PUBLIC_URL/healthz`. Fails → the quick tunnel died (they expire; re-run cloudflared and re-register the webhook). Passes → run `scripts/smoke-atlantis-webhook.sh`. Non-200 → the webhook secret in GitHub does not match `local-secrets/atlantis-webhook-secret`; re-run `make webhook-register`. 200 → the event reached Atlantis, so go to (2).
2. **Event received, no plan.** `kubectl -n atlantis logs deploy/atlantis | tail -50`. `repo not allowlisted` → check `orgAllowlist` in `helm/values/atlantis.yaml` **first**: the chart's default is the literal string `<replace-me>`, which is a regex that matches no repository, and it produces exactly this error. Only after that, look at the repo config. `authentication error` → the PAT lacks `repo` scope, or the webhook is not a GitHub App installation. `no project found` → `dir: tofu` does not match where the `.tf` files actually are.
3. **Plan appears, apply refused.** `execution_mode: plan` is doing exactly what Phase 1 intends. To exercise apply, comment `atlantis apply -d tofu` *and* expect the refusal — then flip `execution_mode` to `apply` in a PR and watch it work. That round trip is the lesson.
4. **Terraform provider cannot reach the cluster.** Atlantis runs `tofu` in-cluster; the kubeconfig it picks up is the pod's ServiceAccount, not your host's. If a provider is configured with `config_path = pathexpand("~/.kube/config")` it will fail in Atlantis even though it works on your laptop. This is the single most common Phase 1 surprise — the fix is an explicit `exec` block using the in-cluster ServiceAccount. Record the fix in the runbook when you hit it, because it will be hit again.
