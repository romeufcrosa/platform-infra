# Vault and secret material

How the platform's secret material works, what the local posture costs, and how
to change it. Written for whoever has to operate this, not for whoever set it
up — the setup is in `tofu/modules/vault/` and the contract is in
`scripts/seed-vault.sh`.

## The contract

Vault runs in **dev mode** and holds a KV v2 store at `secret/`. Ten paths are
seeded. They are the interface between the platform team and the service teams:
Phase 2 services read them by these exact names, so renaming one is a breaking
change for every consumer.

| Path | Value |
|------|-------|
| `platform/go-service/database-url` | `postgres://platform:platform@postgres.platform-system.svc:5432/platform?sslmode=disable` |
| `platform/go-service/jwt-secret` | 32 random bytes, hex |
| `platform/go-service/aws-access-key-id` | `test` |
| `platform/go-service/aws-secret-access-key` | `test` |
| `platform/node-service/database-url` | same DSN as Go, deliberately |
| `platform/node-service/redis-url` | `redis://redis.platform-system.svc:6379/0` |
| `platform/node-service/aws-access-key-id` | `test` |
| `platform/node-service/aws-secret-access-key` | `test` |
| `platform/frontend/nextauth-secret` | 32 random bytes, hex |
| `ministack/endpoint` | `http://ministack.ministack.svc.cluster.local:4566` |

The `test` AWS credentials are **not secrets**. They authenticate nothing; they
exist so a service can exercise the S3/SQS code path against Ministack without
an account.

**`database-url` is one value shared by Go and Node, not two.** The production
design is separate credentials per service so one can be revoked without
revoking the other. That is a deliberate Phase 1 simplification, recorded in
`docs/adr/0005-shared-database-credentials.md`.

### Each value is stored under a key named after the path's leaf

`platform/go-service/database-url` holds the key `database-url`. The
ExternalSecret that consumes it must say so:

```yaml
remoteRef:
  key: platform/go-service/database-url
  property: database-url   # <- required
```

Without `property:`, `remoteRef` selects the **whole** secret and External
Secrets writes a JSON envelope of every key into the Kubernetes Secret. The
service then gets the string `{"database-url":"postgres://..."}` and fails at
connect time with an error that names neither Vault nor External Secrets. This
is not hypothetical — it is what the pipeline did before the field was added,
and it is invisible in every `tofu plan`, every `helm template` and every
`kubectl get` that does not decode the base64.

## Everyday operations

Everything below assumes the port-forward is up (`make port-forwards`, or a
single `kubectl -n vault port-forward svc/vault 8200:8200`).

**Seed / re-seed.** `./scripts/seed-vault.sh` writes all ten paths and reads
every one back, asserting on the value. It is idempotent, and re-running
regenerates `jwt-secret` and `nextauth-secret` — which is the desired behaviour
after a cluster reset, and the reason those two are random rather than fixed.

**Check Vault is up.**

```bash
vault status -address=http://localhost:8200
```

`Sealed: false`, `Storage Type: inmem`, `HA Enabled: false` is the correct
local state. `Sealed: true` means the pod restarted and lost everything; re-run
the seed script.

**Read a secret yourself.**

```bash
export VAULT_TOKEN="$(cat local-secrets/vault-root-token)"
vault kv get secret/platform/go-service/database-url
```

The token lives at `local-secrets/vault-root-token`, mode 0600, gitignored. It is
a `random_password` generated by OpenTofu, and it is never committed and never
an output. `tofu apply` regenerates it only if the state is lost; a normal
apply leaves it alone.

### The token IS in the pod spec. Read this before copying this anywhere.

An earlier revision of this section said the token was "never in a manifest".
**That was false**, and it was false in the way that matters: this is the
document an operator reads before copying the design to a real cluster.

In dev mode the root token is delivered to Vault as an ordinary environment
variable, so it lands in the rendered StatefulSet in plaintext:

```bash
$ helm template vault hashicorp/vault --version 0.28.0 \
    -f helm/values/vault.yaml --set server.dev.devRootToken=FAKETOKEN123 \
  | grep -A2 VAULT_DEV_ROOT_TOKEN_ID
- name: VAULT_DEV_ROOT_TOKEN_ID
  value: FAKETOKEN123
```

Verified against the live cluster, by comparing the StatefulSet's pod template
against the token file (value not printed here):

```bash
$ kubectl --context platform -n vault get sts vault -o jsonpath='{...env[?(@.name=="VAULT_DEV_ROOT_TOKEN_ID")].value}'
# CONFIRMED: identical to the contents of local-secrets/vault-root-token
```

It is **also** in OpenTofu state, in `helm_release.vault.values` — the
`yamlencode` in `tofu/modules/vault/main.tf` puts it there:

```
$ grep -c devRootToken tofu/environments/local/terraform.tfstate
3
```

So the accurate statement is:

| Surface | Carries the token? | Committed to Git? |
|---|---|---|
| `local-secrets/vault-root-token` | yes, plaintext, mode 0600 | **no** — gitignored |
| `tofu .../terraform.tfstate` (`helm_release.values`) | yes, plaintext | **no** — `*.tfstate` gitignored |
| Rendered StatefulSet pod spec | yes, plaintext env var | **no** — generated by Helm at apply |
| `helm/values/vault.yaml` | **no** — `devRootToken: ""` | yes, and it is empty |
| `tofu/outputs.tf` | **no** — only the file *path* is output | yes |

The Global Constraint — no secret values in Git — **does hold**, and is checked
rather than asserted. But "not in Git" is not "not exposed": the token is
readable by anyone who can read the state file, `kubectl get sts vault -o yaml`,
or the StatefulSet's YAML in etcd.

**What has to change before any real deployment:**

1. **Stop using `server.dev`.** Dev mode has no other option — there is no
   chart value that passes the root token without putting it in the pod spec.
   A non-dev Vault has no root token in its environment at all.
2. **Stop handing the operator a root token at all.** The token-based
   `ClusterSecretStore` is what forces a long-lived credential into the chart in
   the first place. Move to `auth.kubernetes` — see the swap procedure below —
   and the secret disappears from the pod spec along with the file.
3. **Then** delete the `local_file` resource and the `local-secrets/` copy.
   Until both are gone, a root token exists on the laptop no matter what the
   store authenticates with.

Steps 2 and 3 are the same change; doing 1 alone changes nothing about the
exposure.

**Check the pipeline is healthy.** The ClusterSecretStore being `Ready` is
*not* sufficient — see below.

```bash
kubectl --context platform get clustersecretstore vault
kubectl --context platform -n dev get externalsecret go-service-credentials
kubectl --context platform -n dev get secret go-service-credentials \
  -o json | python3 -c "import json,sys,base64;[print(f'{k} = {base64.b64decode(v).decode()}') for k,v in sorted(json.load(sys.stdin)['data'].items())]"
```

That last command is the only one that proves a service can read a credential.
Decode it. An envelope in the output is a bug, not a formatting quirk.

### A green ClusterSecretStore is a false all-clear

`clustersecretstore/vault` reported `Ready=True reason=Valid` continuously
through a real outage of the token path. Validating the store only checks that
Vault is reachable; it does not resolve the token reference. During this task's
own bring-up the store was `Ready` while every ExternalSecret was failing with
`SecretSyncedError`. Always read the **ExternalSecret's** status, and if it is
stale, force a re-read:

```bash
kubectl --context platform -n dev annotate externalsecret go-service-credentials \
  force-sync=$(date +%s) --overwrite
```

The operator caches the resolved store, so a corrected
`ClusterSecretStore/vault` does not take effect until the next reconcile. A
freshly applied `ExternalSecret` normally picks it up on its own; an existing
one may not.

### Rotating a secret

The value lives in Vault, not in Git — the ExternalSecret and the seed script
are unchanged by a rotation.

```bash
export VAULT_TOKEN="$(cat local-secrets/vault-root-token)"
vault kv put secret/platform/go-service/jwt-secret jwt-secret="$(openssl rand -hex 32)"
```

The Kubernetes Secret then refreshes on its own within `refreshInterval` (1h on
the example), or immediately with the `force-sync` annotate above. The Go
service must be restarted or made to re-read the file-mounted Secret, because
an env var read at process start does not change underneath a running process.

To add a path: add it to `scripts/seed-vault.sh` (the read-back list too — a
path with no read-back is a path nothing has ever confirmed), add the matching
`secretKey`/`remoteRef`/`property` to
`examples/external-secrets/go-service-credentials.yaml`, and re-run the seed.
`scripts/check-secret-contract.sh` fails if the two disagree.

## What breaks if you copy this to a real cluster

Dev mode is four decisions in one, and every one of them is wrong in production.

1. **In-memory storage.** `Storage Type: inmem`. Vault loses every secret when
   the pod restarts, and with HA disabled there is no second copy. A restart
   silently empties the platform's secret store.
2. **Unseal key = 1 of 1.** `Total Shares: 1, Threshold: 1`. There is no quorum,
   so a single lost key is total loss, and anyone holding the key has
   uncontested root. Production wants 5 shares / 3 threshold on Shamir or, far
   better, auto-unseal against a cloud KMS.
3. **A static root token that never expires.** `random_password` in OpenTofu,
   written to a file on one laptop, mirrored into a Kubernetes Secret. It
   cannot be scoped, cannot be rotated without re-applying, and cannot be
   audited per-caller. Anyone who can read `local-secrets/vault-root-token` is
   root at Vault, forever.
4. **No TLS.** `server: "http://vault.vault.svc.cluster.local:8200"`. The root
   token crosses the network in cleartext on every sync. In-cluster only, and
   still a token anyone with a packet capture on the node can lift.

Also, and separately: dev mode enables only a minimal set of auth methods. The
`kubernetes` auth method that production wants is **not configured**, so the
production store in `tofu/modules/vault/cluster-secret-store.production.yaml`
cannot work against this Vault no matter how the YAML is edited. Adding it is
Vault state, not Kubernetes state.

## Swapping the token-based store for Kubernetes auth

The target state is already written down, in
`tofu/modules/vault/cluster-secret-store.production.yaml`, and is deliberately
**not** applied — nothing reads it, `make validate` does not render it, and
`tofu plan` will never mention it. It is in the tree so the two auth models can
be compared in a review instead of reconstructed from memory later.

What it buys: the operator presents a short-lived, audience-bound JWT that Vault
mints on the strength of the caller's ServiceAccount token, instead of a
permanent credential. There is no long-lived secret to leak, rotate or
revoke, and the JWT's claims are auditable.

In order, because each step is a prerequisite for the next and none of them is
a YAML edit:

1. Replace dev mode with real storage and a real HA topology. Everything below
   is meaningless on a dev-mode Vault — you would be hardening auth against a
   store that empties itself on restart.
2. Serve Vault over TLS and point the store at `https://`, adding a
   `caProvider` block. The local file has no CA because there is nothing to
   trust over plain HTTP.
3. Enable the `kubernetes` auth method, create the `platform-external-secrets`
   role, and set `bound_service_account_names` to `external-secrets-vault` and
   `bound_service_account_namespaces` to `external-secrets`. **Scope the role
   to `platform/*` paths only**, or it is root.
4. Create the `external-secrets-vault` ServiceAccount in the `external-secrets`
   namespace, via OpenTofu — one owner, as with every other object here.
5. Swap the store's `tokenSecretRef` for the `kubernetes` block, and **delete
   `kubernetes_secret.vault_creds` from `tofu/modules/vault/main.tf` in the
   same commit.** Leaving it is the two-owner defect this repo has fought three
   times: OpenTofu keeps re-creating a secret nothing reads, and the plan
   never says why.
6. Delete the local token from `local-secrets/` and remove the `local_file`
   resource. Until that is gone, the root token still exists on the laptop
   regardless of what the store authenticates with.

Step 5 is the one that gets skipped, and it is the only one that causes a
permanent diff. Do it in the same commit.

## The ownership rule (R29b)

An object is declared in exactly one place.

- OpenTofu owns: the `StatefulSet/vault`, its three Services, the
  `ServiceAccount`, the `ClusterSecretStore/vault` and the
  `external-secrets-vault-creds` Secret.
- **Nobody owns, by design:** the `ExternalSecret/go-service-credentials`
  example, which lives at
  `examples/external-secrets/go-service-credentials.yaml`. It is applied by
  nothing and synced by nothing. It is a template, not a component.

`kubernetes/platform-system/` is synced with `recurse: true`, `prune: true` and
`selfHeal: true`, so a workload object declared there *and* in an OpenTofu
module is a reconcile loop: ArgoCD reverts OpenTofu's change, the next
`tofu apply` reverts ArgoCD's, and `tofu plan` reports clean the whole time
because neither tool is wrong about its own copy. The check that catches it:

```bash
kubectl kustomize kubernetes/platform-system \
  | grep -cE '^kind: (Deployment|Service|ServiceAccount|Job|Namespace)'
```

Must print `0`.

The example is not in that base for a second reason as well. The
`platform-system` AppProject deliberately lists only the eight platform
namespaces in `spec.destinations` and omits `dev`, `staging` and `prod`; ArgoCD
validates a resource's namespace against the AppProject, not the Application's
destination, so a service-namespace ExternalSecret could not be synced by that
Application at all. Widening the invariant to accommodate an example would have
cost more than the example was worth — and the ownership is right the other way
round anyway, since a service's credentials manifest belongs to the service's
repository. See `examples/README.md`.

There is exactly one copy of that manifest. It used to be duplicated into
`tofu/modules/vault/external-secrets-example.yaml`, where no tool read it; R29b
applies to files as well as to objects, and the unread copy is the one that
drifts.
